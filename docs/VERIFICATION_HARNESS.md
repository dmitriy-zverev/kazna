# Швы для независимой приёмки

Чёрный ящик (репозиторий [kazna-verification](https://github.com/dmitriy-zverev/kazna-verification)) проверяет **собранный Docker-образ** Казны. Внутренние пакеты и тестовые хуки в production-коде не используются. Ниже — только переменные окружения и сетевые правила, которые сервис должен поддерживать для стенда.

## Эмулятор ЮKassa

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `YOOKASSA_API_URL` | `https://api.yookassa.ru` | Базовый URL API провайдера. На стенде указывает на fake-yookassa (часто через Toxiproxy). |

Адаптер ЮKassa в Казне должен брать базовый URL из этой переменной, не хардкодить production endpoint.

## Окно идемпотентности провайдера

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PROVIDER_IDEMPOTENCY_WINDOW` | `24h` | Длительность, в течение которой повтор с тем же ключом провайдера считается тем же запросом. На стенде задаётся короткое значение (например `30s`), чтобы тесты истечения окна не ждали сутки. |

## Исходящие webhook приложений

Стенд поднимает `webhook-sink` в той же Docker-сети.

| Правило | Значение |
|---|---|
| `APP_ENV=development` или `staging` | Разрешены URL вида `http://webhook-sink:8080/...` для регистрации в приложении. |
| `APP_ENV=production` | Запрещены private IP, localhost, link-local и имена внутренних сервисов в URL webhook приложения (см. [SECURITY.md](SECURITY.md)). |

Отдельный security-прогон в kazna-verification поднимает Казну с `APP_ENV=production` и ожидает отказ при сохранении webhook на внутренний адрес.

## Что стенд не требует от Казны

- Отдельного test-only API для сброса БД или подмены статусов.
- Встраивания pytest или Python SDK в образ API.
- Чтения исходников Казны при формировании ожидаемого результата (только OpenAPI, этот документ, [FINANCIAL_INVARIANTS.md](FINANCIAL_INVARIANTS.md) и [TECHNICAL_PLAN.md](TECHNICAL_PLAN.md)).

## Запуск приёмки

Обязательные сценарии из раздела 15 [TECHNICAL_PLAN.md](TECHNICAL_PLAN.md) выполняются в CI репозитория kazna-verification. Приёмочный статус релиза определяется результатом этого прогона. Интеграционные тесты внутри Казны (раздел 14, этап 7) остаются обязательными и выполняются в её CI, но не заменяют приёмку.
