# Технический план разработки универсального платёжного сервиса
### MVP 1.0 · Go + PostgreSQL + Docker + YooKassa

**Цель проекта:** разработать самостоятельный, надёжный платёжный микросервис, который централизованно обслуживает несколько приложений и предоставляет максимально простой API для приёма платежей.

Главный принцип: **любое приложение должно подключать оплату за несколько минут, используя собственный API-ключ и функцию `pay()`, без непосредственной интеграции с ЮKassa.**

План рассчитан на разработку с использованием ИИ-агентов, поэтому включает архитектурные решения, структуру проекта, контракты API, базу данных, алгоритмы, этапы реализации и критерии приёмки.

## 1. Концепция MVP

### 1.1. Что мы разрабатываем

Создаём отдельный сервис, который разворачивается на сервере с помощью Docker Compose и имеет собственную базу данных.

Сервис отвечает за регистрацию подключаемых приложений, управление API-ключами, хранение настроек платёжных провайдеров, создание платежей, отслеживание их состояния и уведомление приложений о результатах.

Для первого релиза используется только ЮKassa. Возможность подключения других провайдеров закладывается архитектурно, но их реализация откладывается.

### 1.2. Как выглядит работа с точки зрения разработчика

Первоначальная настройка приложения:

1. Разработчик открывает административную панель платёжного сервиса.
2. Создаёт приложение и указывает его название.
3. Подключает ЮKassa, передав `shop_id` и `secret_key`.
4. Получает API-ключ своего приложения.
5. Устанавливает SDK или использует REST API.

В дальнейшем для создания оплаты достаточно:

```python
from kazna import PaymentClient

payments = PaymentClient(
    api_key="app_live_xxxxxxxxx",
    base_url="https://payments.example.com"
)

payment = await payments.pay(
    amount=49900,
    order_id="order_123",
    description="Подписка Pro"
)

print(payment.checkout_url)
```

Здесь `amount=49900` означает 499 рублей в копейках. Все суммы внутри нашего API передаются целыми числами в минимальных денежных единицах.

Пользователь переходит по `checkout_url` и оплачивает заказ.

Для проверки результата:

```python
payment = await payments.get(
    payment_id="pay_123"
)

if payment.status == "succeeded":
    await activate_subscription()
```

В рабочем приложении выдача продукта должна выполняться идемпотентно. Предпочтительный механизм подтверждения — серверное событие об успешной оплате, а не переход пользователя обратно на сайт.

Всё взаимодействие с ЮKassa, включая создание платежа, повторные запросы, получение статусов и обработку ошибок, реализуется в нашем сервисе.

### 1.3. Функциональные границы MVP

В первую версию входят создание и управление приложениями, отдельные API-ключи, подключение магазинов ЮKassa, одностадийные платежи, выдача ссылок на оплату, проверка статуса, обработка входящих webhook, фоновая проверка платежей, исходящие уведомления, журнал операций и тестовая среда.

Также необходимы защита от двойного создания операций, восстановление после сбоев, резервное копирование и базовый мониторинг.

Возвраты желательно включить в версию 1.0, но после завершения основного платёжного сценария.

Создание подписок, автосписания, собственные платёжные формы, маршрутизация между несколькими провайдерами, мультивалютность и полноценный биллинг в MVP не входят.

Важно: сервис не заменяет регистрацию магазина в ЮKassa и заключение необходимых договоров. Он устраняет необходимость повторно разрабатывать интеграцию для каждого продукта.

# 2. Архитектура системы

## 2.1. Общая схема

```text
                  CLIENT APPLICATIONS
                          
          ┌───────────┬───────────┐
          │           │           │
       SaaS App     Website      Bot
          │           │           │
          └───────────┼───────────┘
                      │
                REST API / SDK
                      │
                      ▼
                HTTPS / Caddy
                      │
                      ▼
       ┌────────────────────────────┐
       │         PAYMENT API        │
       │                            │
       │  Authentication            │
       │  Application Management    │
       │  Payment Management        │
       │  Provider Integration      │
       │  Webhook Processing        │
       │  Event Management          │
       └──────────────┬─────────────┘
                      │
                      ▼
                PostgreSQL
                      ▲
                      │
       ┌──────────────┴─────────────┐
       │       PAYMENT WORKER       │
       │                            │
       │  Payment Reconciliation    │
       │  Retry Processing          │
       │  Event Delivery            │
       │  Recovery Jobs             │
       └──────────────┬─────────────┘
                      │
                      ▼
                 YooKassa API
```

В систему входят два основных процесса: API-сервер и фоновый worker.

Оба разрабатываются на Go, используют общие бизнес-модули и PostgreSQL.

API-сервер принимает запросы приложений, а worker выполняет отложенные операции.

PostgreSQL выступает единым источником достоверного состояния платежей и очереди фоновых задач.

## 2.2. Архитектурный стиль

**Выбираем модульный монолит, а не набор микросервисов.**

Это принципиальное решение.

Несмотря на то что продукт является самостоятельным микросервисом относительно остальных приложений, внутри него на этапе MVP не требуется создавать отдельные сетевые сервисы для авторизации, платежей, событий и провайдеров.

Гораздо удобнее поддерживать один Go-проект, разделённый на независимые модули.

Это позволит сократить количество точек отказа, упростить разработку и тестирование, уменьшить потребление ресурсов и облегчить работу ИИ-агентов.

Для масштабирования API и worker должны поддерживать запуск нескольких экземпляров.

## 2.3. Технологический стек

| Компонент | Технология | Назначение |
|---|---|---|
| Backend | Go | Основная бизнес-логика |
| HTTP API | net/http + Chi | REST API |
| Database | PostgreSQL 17+ | Платежи, приложения, события |
| Database driver | pgx | Доступ к PostgreSQL |
| SQL | sqlc + SQL-запросы | Типобезопасная работа с БД |
| Миграции | golang-migrate | Версионирование схемы |
| Worker | Go | Асинхронные операции |
| Reverse proxy | Caddy | HTTPS |
| Deployment | Docker Compose | Развёртывание |
| API specification | OpenAPI 3.1 | Контракты и документация |
| Python SDK | httpx | Интеграция с Python |
| TypeScript SDK | fetch | Интеграция с JS/TS |
| Тестирование | Go testing + Testcontainers | Unit- и integration-тесты |
| Мониторинг | Prometheus-совместимые метрики | Наблюдение за работой |

Использование PostgreSQL в качестве очереди позволит не добавлять Redis и RabbitMQ в MVP.

Для первых нескольких приложений такой архитектуры достаточно при корректной настройке индексов, транзакций и фоновой обработки.

## 2.4. Основные правила архитектуры

Все изменения состояния платежей должны проходить через единый доменный сервис. HTTP-обработчики и SDK не должны содержать платёжную бизнес-логику.

Работа с ЮKassa должна осуществляться через адаптер провайдера.

Запросы к внешнему провайдеру нельзя выполнять внутри длительной транзакции PostgreSQL.

У каждого платежа должен быть постоянный внутренний идентификатор, независимый от идентификатора ЮKassa.

Любая операция, затрагивающая деньги, должна быть идемпотентной.

При неизвестном результате внешнего запроса система не должна считать операцию неуспешной и создавать новую автоматически.

# 4. Проектирование базы данных

Это один из самых важных этапов разработки.

Платёжная система должна сохранять не только текущие статусы, но и историю операций, попыток обращения к провайдеру и доставки событий.

## 4.1. Основные сущности

Предлагаю использовать следующую модель данных.

### Таблица `applications`

Хранит зарегистрированные приложения.

| Поле | Тип | Назначение |
|---|---|---|
| id | UUID | Идентификатор приложения |
| name | VARCHAR | Название |
| slug | VARCHAR | Уникальное системное имя |
| status | VARCHAR | active / disabled |
| default_return_url | TEXT | URL возврата |
| webhook_url | TEXT | URL событий приложения |
| created_at | TIMESTAMPTZ | Дата создания |
| updated_at | TIMESTAMPTZ | Дата изменения |

У каждого приложения собственные платежи, API-ключи и настройки.

### Таблица `api_keys`

Отвечает за авторизацию подключённых приложений.

```text
id
application_id
key_prefix
key_hash
name
permissions
expires_at
last_used_at
revoked_at
created_at
```

API-ключ создаётся с использованием криптографически безопасного генератора случайных чисел.

Сервер показывает его владельцу один раз.

В базе хранится только криптографический хеш ключа. Для поиска используется отдельный публичный идентификатор или префикс.

Это позволит отзывать ключи без удаления приложения, выполнять ротацию и ограничивать права.

### Таблица `provider_accounts`

Хранит настройки платёжных провайдеров.

```text
id
provider
shop_id
encrypted_secret_key
environment
status
created_at
updated_at
```

Например:

```text
provider: yookassa
shop_id: 123456
environment: production
status: active
```

Одна учётная запись ЮKassa может использоваться несколькими приложениями, если это соответствует бизнес-схеме и настройкам магазина.

Поэтому связь между приложениями и провайдерами лучше реализовать отдельной таблицей `application_providers`.

Это даст возможность подключить один магазин к нескольким собственным SaaS-продуктам без дублирования ключей.

### Таблица `payments`

Основная таблица платёжных операций.

```text
id
application_id
provider_account_id

order_id
attempt_number

provider
provider_payment_id

amount_minor
currency
description

status
checkout_url

created_at
updated_at
completed_at
next_check_at

metadata
```

`id` — внутренний идентификатор платежа.

`order_id` — идентификатор заказа в приложении.

`attempt_number` — номер попытки оплаты заказа.

`provider_payment_id` — идентификатор платежа в ЮKassa.

`amount_minor` — сумма целым числом в копейках.

`next_check_at` — время следующей проверки платежа.

Важный момент: **один заказ может иметь несколько попыток оплаты, но система не должна допускать одновременного существования нескольких активных попыток одного заказа**.

Если пользователь отменил первую оплату, приложение сможет создать новую попытку.

Но пока предыдущая попытка не завершена достоверным терминальным статусом, новую создавать нельзя.

Это уменьшает риск двух успешных оплат одного заказа.

### Таблица `payment_operations`

Хранит операции взаимодействия с внешним провайдером.

```text
id
payment_id
operation_type

idempotency_key
request_hash

status
attempt_count

last_error
started_at
completed_at
created_at
```

Она особенно важна для обработки неоднозначных ситуаций.

Например, если сервис отправил запрос на создание платежа, но соединение оборвалось, запись об операции уже должна существовать.

Worker сможет восстановить её выполнение.

Необходимо также сохранять неизменяемые параметры внешнего запроса, достаточные для его безопасного повторения.

Секретные ключи и конфиденциальные данные клиентов в этой таблице хранить не требуется.

### Таблица `outbox_events`

Очередь исходящих событий.

```text
id
application_id
event_type
aggregate_id
payload

created_at
```

Эта таблица является постоянным журналом событий.

Например:

```text
event_type: payment.succeeded
aggregate_id: pay_123
```

Создание записи об успешной оплате и соответствующего события должно происходить в одной транзакции PostgreSQL.

### Таблица `webhook_deliveries`

Хранит состояние доставки событий приложениям.

```text
id
event_id
application_id
destination_url

status
attempt_count

next_retry_at
last_http_status
last_error

delivered_at
created_at
```

Разделение событий и попыток доставки позволит сохранять историю даже после успешной отправки webhook.

### Дополнительные таблицы

Потребуются `idempotency_requests` для защиты внешнего API от повторных запросов, `incoming_webhooks` для сохранения уведомлений провайдера и `audit_logs` для журнала административных действий.

Для реализации возвратов отдельно создаётся таблица `refunds`.

## 4.2. Ограничения на уровне базы

На уровне PostgreSQL необходимо создать уникальные ограничения для пары `application_id + idempotency_key`, комбинации `application_id + order_id + attempt_number` и идентификатора внешней операции в рамках провайдера.

Также необходим частичный уникальный индекс, не допускающий одновременно несколько незавершённых попыток одного заказа.

Важно, чтобы эти ограничения обеспечивались самой базой данных, а не только проверками в Go.

Два параллельных запроса могут одновременно пройти программную проверку, поэтому без транзакций и ограничений БД защита от дубликатов будет неполной.

# 5. Контракт REST API

Перед реализацией бизнес-логики необходимо зафиксировать OpenAPI-спецификацию.

Она станет единым контрактом для backend, SDK и тестов.

## 5.1. Создание платежа

```http
POST /v1/payments
Authorization: Bearer app_live_xxxxx
Idempotency-Key: order_123_attempt_1
Content-Type: application/json
```

Тело запроса:

```json
{
  "order_id": "order_123",
  "amount": 49900,
  "currency": "RUB",
  "description": "Подписка Pro",
  "return_url": "https://app.example.com/billing",
  "customer": {
    "email": "user@example.com"
  },
  "metadata": {
    "user_id": "user_123",
    "plan": "pro"
  }
}
```

Для MVP поддерживается валюта `RUB`.

Сумма передаётся в копейках в формате целого числа. Сервер самостоятельно преобразует её в формат ЮKassa `"499.00"`.

Ответ при успешном создании:

```http
HTTP/1.1 201 Created
```

```json
{
  "id": "pay_abc123",
  "order_id": "order_123",
  "attempt_number": 1,
  "status": "pending",
  "amount": 49900,
  "currency": "RUB",
  "checkout_url": "https://yoomoney.ru/...",
  "provider": "yookassa",
  "created_at": "2026-10-12T10:35:00Z"
}
```

Провайдерские реквизиты и секретные ключи никогда не передаются приложению.

### Обработка долгого создания платежа

API не должно бесконечно ожидать ответа ЮKassa.

Если операция ещё выполняется или её результат неясен, сервер может вернуть:

```http
HTTP/1.1 202 Accepted
```

```json
{
  "id": "pay_abc123",
  "status": "creating",
  "checkout_url": null,
  "retry_after": 2
}
```

SDK в таком случае может автоматически ожидать результата ограниченное время.

Если создать платёж не удалось достоверно, клиент получает нормализованную ошибку. Если результат неизвестен, сервис возвращает соответствующий статус и продолжает восстановление.

**При сетевом тайм-ауте нельзя автоматически создавать новый платёж с другим ключом идемпотентности.**

## 5.2. Получение информации о платеже

```http
GET /v1/payments/{payment_id}
```

Пример ответа:

```json
{
  "id": "pay_abc123",
  "order_id": "order_123",
  "status": "succeeded",
  "amount": 49900,
  "currency": "RUB",
  "paid_at": "2026-10-12T10:36:14Z"
}
```

Дополнительно необходимо поддержать поиск платежей по `order_id` в рамках приложения.

```http
GET /v1/payments?order_id=order_123
```

Этот запрос особенно полезен, когда приложение перезапустилось и потеряло локальную информацию о платеже.

## 5.3. Повторная попытка оплаты

Для отменённого платежа добавляется отдельный метод:

```http
POST /v1/orders/{order_id}/payment-attempts
```

Он создаёт новую попытку только после проверки, что предыдущая уже находится в терминальном состоянии.

Это безопаснее, чем автоматически создавать новый внешний платёж при каждом повторном вызове `pay()`.

## 5.4. Возвраты

После готовности основного сценария добавляем:

```http
POST /v1/payments/{payment_id}/refunds
```

```json
{
  "amount": 49900,
  "reason": "customer_request"
}
```

Для возвратов должны существовать отдельные ключи идемпотентности и собственная модель состояний.

При этом возврат не должен заменять статус оригинального платежа `succeeded`: это самостоятельная финансовая операция.

ЮKassa поддерживает полные и частичные возвраты, однако доступность частичного возврата зависит от способа оплаты. [ЮKassa](https://yookassa.ru/developers/payment-acceptance/after-the-payment/refunds?utm_source=chatgpt.com)

## 5.5. Нормализованные ошибки

API должно возвращать одинаковую структуру ошибок независимо от провайдера.

Например:

```json
{
  "error": {
    "code": "PROVIDER_UNAVAILABLE",
    "message": "Payment provider temporarily unavailable",
    "retryable": true,
    "request_id": "req_123"
  }
}
```

Предусматриваем коды `INVALID_REQUEST`, `UNAUTHORIZED`, `PAYMENT_NOT_FOUND`, `IDEMPOTENCY_CONFLICT`, `PAYMENT_ALREADY_SUCCEEDED`, `PROVIDER_UNAVAILABLE`, `PROVIDER_TIMEOUT`, `PROVIDER_AUTH_FAILED` и `PAYMENT_STATE_UNKNOWN`.

Серверные ошибки не должны раскрывать `secret_key`, строки подключения к БД или другие внутренние данные.

# 6. Реализация платёжного ядра

Это центральный модуль системы.

## 6.1. Модель состояний

Предлагаю следующую внутреннюю модель.

```text
             CREATED
                │
                ▼
             CREATING
                │
         ┌──────┴──────┐
         │             │
         ▼             ▼
      PENDING     CREATION_UNKNOWN
         ▲             │
         └─────────────┘
         │
    ┌────┴─────┐
    │          │
    ▼          ▼
 SUCCEEDED   CANCELED
```

`CREATED` означает, что локальная операция создана.

`CREATING` — выполняется обращение к провайдеру.

`CREATION_UNKNOWN` — запрос мог быть обработан провайдером, но достоверный результат ещё не получен.

`PENDING` — платёж существует и ожидает завершения.

`SUCCEEDED` — оплата подтверждена.

`CANCELED` — провайдер подтвердил отмену или окончательное неуспешное завершение.

Для MVP используем одностадийную оплату. В двухстадийной схеме дополнительно появится состояние ожидания списания `waiting_for_capture`.

Внешние статусы не должны напрямую управлять внутренними переходами.

Создаём отдельную state machine, которая проверяет допустимость изменения состояния.

Например, нельзя переводить `SUCCEEDED` обратно в `PENDING` из-за запоздавшего уведомления.

## 6.2. Алгоритм создания платежа

Алгоритм должен быть следующим.

**Первый этап — аутентификация.** Сервис проверяет API-ключ, определяет приложение и доступную платёжную конфигурацию.

**Второй этап — проверка запроса.** Проверяется сумма, валюта, идентификатор заказа, допустимость `return_url`, параметры чека и ограничения приложения.

**Третий этап — идемпотентность.** Система проверяет, существует ли операция с таким ключом.

Если существует операция с теми же параметрами, возвращается её текущий результат.

Если ключ совпадает, а параметры отличаются, возвращается `409 Conflict`.

**Четвёртый этап — локальная транзакция.** Создаётся запись платежа и операция обращения к ЮKassa. Сохраняются параметры, позволяющие повторить внешний запрос без изменений.

**Пятый этап — вызов провайдера.** Сервис обращается к ЮKassa, передавая заранее сохранённый ключ идемпотентности.

**Шестой этап — сохранение результата.** После ответа сохраняются `provider_payment_id`, состояние, URL оплаты и остальные необходимые данные.

**Седьмой этап — ответ приложению.** Возвращается платёж и ссылка на оплату.

Если на любом этапе происходит сбой, система должна сохранять достаточную информацию для восстановления.

## 6.3. Двойная идемпотентность

Нам нужны два независимых уровня защиты.

Первый — между клиентским приложением и нашим платёжным сервисом.

Второй — между нашим сервисом и ЮKassa.

Их ключи должны храниться отдельно.

Это особенно важно, потому что ЮKassa гарантирует идемпотентность запросов в течение 24 часов. После окончания этого периода запрос с прежним ключом может быть обработан как новый. Максимальная длина ключа — 64 символа. [ЮKassa](https://yookassa.ru/developers/using-api/interaction-format?utm_source=chatgpt.com)

Поэтому для каждой внешней операции создаём собственный UUID, который сохраняем до первого обращения к провайдеру.

При ошибке повторяем операцию с тем же UUID и неизменённым телом запроса.

Если результат не удалось установить до окончания периода гарантированной идемпотентности, переводим операцию в состояние `NEEDS_REVIEW`.

**Автоматически повторять создание платежа после истечения этого периода запрещено**, пока не установлено, существовала ли исходная операция.

Это важное требование безопасности, которое необходимо явно зафиксировать в ТЗ для ИИ-агентов.

# 7. Интеграция с ЮKassa

## 7.1. Универсальный интерфейс провайдера

Создаём интерфейс:

```go
type PaymentProvider interface {
    CreatePayment(
        ctx context.Context,
        req CreatePaymentRequest,
    ) (CreatePaymentResponse, error)

    GetPayment(
        ctx context.Context,
        providerPaymentID string,
    ) (ProviderPayment, error)

    CreateRefund(
        ctx context.Context,
        req CreateRefundRequest,
    ) (RefundResponse, error)
}
```

Интерфейс служит внутренним контрактом, а конкретная реализация находится в пакете `providers/yookassa`.

При добавлении другого провайдера основные бизнес-модули не должны изменяться.

## 7.2. Создание платежа ЮKassa

Для MVP используем:

```http
POST https://api.yookassa.ru/v3/payments
```

Авторизация осуществляется через HTTP Basic Auth с идентификатором магазина и секретным ключом.

Запрос включает `capture: true`, сумму, описание, идентификатор заказа в metadata и подтверждение типа `redirect`.

ЮKassa возвращает объект платежа, а для сценария с перенаправлением — `confirmation_url`, на который нужно отправить покупателя. [ЮKassa](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process?utm_source=chatgpt.com)

Наш сервис преобразует этот URL в универсальное поле `checkout_url`.

## 7.3. Работа с ошибками провайдера

Создаём отдельный HTTP-клиент с ограниченным временем ожидания соединения и ответа.

Должны обрабатываться ошибки подключения, тайм-ауты, HTTP 400/401/403, ограничение запросов HTTP 429 и серверные ошибки 5xx.

При HTTP 429 используется exponential backoff с небольшим случайным отклонением интервала.

ЮKassa документирует ограничение количества запросов и рекомендует увеличивать интервалы при получении `too_many_requests`. [ЮKassa](https://yookassa.ru/developers/using-api/lists?utm_source=chatgpt.com)

Для каждого подключённого магазина вводим ограничение конкурентных запросов.

Необходимо также разделить повторяемые сетевые ошибки и окончательные ошибки валидации.

При ошибке авторизации бессмысленно бесконечно повторять запрос: подключение должно перейти в состояние, требующее вмешательства администратора.

## 7.4. Фискализация

У каждого приложения или магазина должна быть конфигурация формирования чеков.

Для фиксированного товара можно хранить шаблон чека, а для произвольного заказа приложение передаёт позиции, стоимость, количество и необходимые налоговые параметры.

Это позволит не усложнять каждый вызов `pay()` для типовых подписок.

При этом нельзя подставлять произвольный универсальный налоговый код для всех клиентов.

ЮKassa поддерживает разные схемы работы с чеками, а набор обязательных данных зависит от подключённого решения. Например, при определённых сценариях чек передаётся вместе с платежом, а при других формируется отдельным запросом. [ЮKassa](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/yoomoney/payments?utm_source=chatgpt.com)

Для первого релиза нужно выбрать и протестировать конкретный поддерживаемый режим фискализации.

# 8. Отслеживание платежей

Здесь предлагаю сделать то, что соответствует твоей идее простого подключения.

**Сервис должен корректно работать даже без настройки webhook в ЮKassa.**

Это позволит подключить новое приложение, передав только реквизиты магазина, и сразу создавать платежи.

## 8.1. Базовый режим: автоматическая проверка статуса

После создания платежа система планирует фоновую проверку.

Worker обращается к:

```http
GET /v3/payments/{payment_id}
```

Затем получает актуальное состояние.

Предлагаю адаптивную стратегию проверки:

| Возраст незавершённого платежа | Интервал проверки |
|---|---|
| Первые 5 минут | 15–30 секунд |
| От 5 до 30 минут | Около 1 минуты |
| От 30 минут до 2 часов | 5 минут |
| Далее | 10–15 минут |

Это стартовые настройки нашего worker, а не обязательные интервалы ЮKassa.

Периодичность должна зависеть от доступных лимитов API, количества платежей и способа оплаты.

Worker прекращает регулярные проверки только при достоверном терминальном состоянии. Зависшие операции должны попадать в отдельную очередь диагностики.

Так как некоторые способы оплаты завершаются не мгновенно, нельзя автоматически помечать платёж отменённым только потому, что прошло несколько минут.

## 8.2. Дополнительный режим: webhook ЮKassa

Когда требуется быстрее получать события и уменьшить количество запросов, пользователь может настроить webhook в личном кабинете ЮKassa.

Для подключения через `shop_id` и `secret_key` это именно настройка в кабинете. Программное управление webhook через API предусмотрено для OAuth-интеграций. [ЮKassa](https://yookassa.ru/developers/using-api/webhooks?utm_source=chatgpt.com)

В панели нашего сервиса показываем готовый URL:

```text
https://payments.example.com/webhooks/yookassa/{connection_id}
```

После его настройки webhook становится основным источником оперативных событий, а периодическая сверка остаётся резервным механизмом.

Если несколько приложений используют один магазин ЮKassa, одного подключения webhook для магазина достаточно: маршрутизация к приложению выполняется по сохранённой связи внешнего платежа с внутренним.

## 8.3. Обработка входящего webhook

Алгоритм обработки:

Сервер принимает уведомление, проверяет формат запроса, идентифицирует конфигурацию провайдера и сохраняет входящее событие.

После надёжного сохранения возвращает ЮKassa HTTP 200.

Worker проверяет полученное уведомление и запрашивает платёж через авторизованный API ЮKassa.

Затем сверяет идентификатор магазина, сумму, валюту и принадлежность платежа нужному приложению.

Если состояние действительно изменилось, обновляет запись в PostgreSQL.

Одновременно создаёт исходящее событие для приложения.

Если уведомление приходит повторно, никаких повторных бизнес-изменений быть не должно.

ЮKassa повторно доставляет неподтверждённые уведомления ограниченное время — 24 часа. Поэтому сохранять входящие события и иметь механизм сверки важно даже при использовании webhook. [ЮKassa](https://yookassa.ru/developers/using-api/webhooks?utm_source=chatgpt.com)

# 9. Надёжная доставка событий приложениям

Это отдельный обязательный модуль.

Сам факт успешной оплаты ещё не означает, что подключённое приложение узнало об этом.

## 9.1. Transactional Outbox

Выполняем в одной транзакции:

```sql
BEGIN;

UPDATE payments
SET status = 'succeeded'
WHERE id = $1
  AND status NOT IN ('succeeded', 'canceled');

INSERT INTO outbox_events (...);

COMMIT;
```

Это иллюстрация принципа. В реальной реализации вставка события должна выполняться только после подтверждённого допустимого перехода состояния, с защитой от повторной вставки.

В результате невозможно зафиксировать новый статус без соответствующей записи о событии.

## 9.2. Worker доставки

Фоновый обработчик извлекает события из PostgreSQL, используя блокировки `FOR UPDATE SKIP LOCKED`.

После этого отправляет HTTP POST на заранее зарегистрированный адрес приложения:

```http
POST https://app.example.com/api/payment-events
```

```json
{
  "id": "evt_123",
  "type": "payment.succeeded",
  "created_at": "2026-10-12T10:36:14Z",
  "data": {
    "payment_id": "pay_abc123",
    "order_id": "order_123",
    "amount": 49900,
    "currency": "RUB"
  }
}
```

Каждое событие получает постоянный идентификатор.

При ошибке доставки worker повторяет отправку.

Для доставки используется отдельный секрет приложения и HMAC-SHA256-подпись тела запроса с временной меткой.

На стороне приложения SDK проверяет подпись, допустимость времени и идентификатор события.

Важно: **система гарантирует повторную доставку, а не отсутствие повторных сообщений**.

Поэтому обработчик приложения должен уметь принимать одно и то же событие несколько раз.

Для особо важных операций, например активации подписки, приложение должно сохранять обработанный `event_id` в своей базе.

## 9.3. Поведение при недоступности приложения

Предположим, приложение не отвечает 30 минут.

Наш сервис не теряет событие.

Оно остаётся в PostgreSQL, а worker делает повторные попытки с увеличением интервала.

Если приложение недоступно слишком долго, событие переводится в состояние `delivery_failed` и создаётся предупреждение администратору.

Само событие остаётся доступным для повторной отправки.

# 10. SDK: самая важная часть пользовательского опыта

Я бы относился к SDK как к полноценной части продукта, а не дополнительной библиотеке.

Именно здесь мы выигрываем у прямой интеграции с ЮKassa.

## 10.1. Python SDK

Основной интерфейс:

```python
payments = PaymentClient(
    api_key="app_live_xxxxx",
    base_url="https://payments.example.com"
)
```

Создание оплаты:

```python
payment = await payments.pay(
    order_id="order_123",
    amount=49900,
    description="Подписка Pro"
)
```

Проверка:

```python
status = await payments.is_paid(
    order_id="order_123"
)
```

Получение объекта:

```python
payment = await payments.get(
    payment_id="pay_123"
)
```

Повторная попытка:

```python
payment = await payments.retry(
    order_id="order_123"
)
```

Возврат:

```python
refund = await payments.refund(
    payment_id="pay_123",
    amount=49900
)
```

Для обработки webhook предоставляем готовые интеграции с популярными web-фреймворками.

Например, FastAPI:

```python
from fastapi import FastAPI
from kazna.integrations.fastapi import payment_router

app = FastAPI()

app.include_router(
    payment_router(payments),
    prefix="/webhooks/payments"
)
```

Приложение может зарегистрировать собственную бизнес-логику обработки успешных оплат.

SDK отвечает за HTTP-слой, проверку подписи и преобразование события в типизированный объект.

**При этом SDK не должен автоматически выполнять бизнес-действия в приложении.** Выдача товара, активация подписки и изменение баланса остаются ответственностью самого продукта.

## 10.2. TypeScript SDK

Сохраняем аналогичный интерфейс:

```typescript
const payments = new PaymentClient({
  apiKey: process.env.PAYMENT_API_KEY!,
  baseUrl: process.env.PAYMENT_API_URL!
});

const payment = await payments.pay({
  orderId: "order_123",
  amount: 49900,
  description: "Подписка Pro"
});
```

Важное ограничение: SDK с секретным API-ключом предназначен для серверного кода.

Нельзя подключать его непосредственно в браузере и передавать туда ключ.

Frontend обращается к backend своего приложения, который создаёт платёж и возвращает безопасную ссылку.

## 10.3. Требования к SDK

SDK должен иметь типизированные запросы и ответы, централизованную обработку ошибок, настраиваемые тайм-ауты, безопасные повторные попытки и поддержку асинхронного использования.

Он не должен самостоятельно генерировать новый идентификатор платёжной попытки при каждом сетевом повторе.

Повторный вызов `pay()` для одного заказа должен возвращать существующую попытку, если параметры совпадают.

Также в SDK необходимо предусмотреть возможность передачи собственного HTTP-клиента для тестирования.

## 10.4. Документация интеграции

Документацию организуем вокруг готовых сценариев.

Основной Quick Start должен содержать инструкцию подключения магазина, получения ключа, создания платежа и подтверждения оплаты.

Цель — чтобы новый проект мог реализовать базовую оплату, используя один экран документации.

Отдельные примеры нужны для FastAPI, Django, Node.js и Telegram-ботов.


Проверка соединения должна выполнять безопасный запрос к API провайдера, не создающий реальный платёж.

Если проверка не удалась, показываем понятную причину: неверные реквизиты, недоступность API или ошибка сети.

Секретный ключ после сохранения нельзя прочитать обратно через API панели.

## 11.3. Мониторинг платежей

Минимальный экран истории операций:

```text
Payments
───────────────────────────────────────────

ID        Order       Amount     Status

pay_001   order_101   499 RUB    Succeeded
pay_002   order_102   199 RUB    Pending
pay_003   order_103   799 RUB    Canceled
```

При открытии платежа администратор видит состояние, время создания, историю запросов, последнее подтверждение ЮKassa и статус доставки события приложению.

Это очень полезно при отладке.

## 11.4. Техническая реализация

Для MVP я бы использовал простой серверный интерфейс на Go с HTML-шаблонами и HTMX.

Так мы избежим необходимости содержать отдельный frontend-проект на React.

Административная панель должна быть защищена отдельной авторизацией администратора и желательно доступна только через VPN или ограниченный набор доверенных адресов.

API-ключи приложений не должны давать доступ к административному интерфейсу.

# 12. Безопасность

Для платёжного сервиса этот раздел обязателен уже в MVP.

## 12.1. Хранение ключей ЮKassa

Секреты храним в зашифрованном виде с использованием аутентифицированного шифрования, например AES-256-GCM.

Главный ключ шифрования хранится отдельно от PostgreSQL, через секрет окружения или другой защищённый механизм.

При компрометации одной только базы данных злоумышленник не должен получить открытые ключи провайдера.

В логах запрещено сохранять секреты, заголовки авторизации и полные тела запросов с конфиденциальными данными.

Предусматриваем ротацию мастер-ключа и ключей провайдера.

## 12.2. Разделение приложений

Каждый запрос должен выполняться в контексте конкретного `application_id`.

Этот идентификатор определяется сервером по API-ключу.

Приложение не может самостоятельно указать чужой `application_id` и получить доступ к его операциям.

Все запросы к базе должны фильтроваться по соответствующему приложению.

## 12.3. Проверка URL

`return_url` должен соответствовать разрешённым доменам приложения.

Это предотвращает использование сервиса для перенаправления покупателей на произвольные сайты.

Адреса доставки webhook также должны проверяться.

Для пользовательских webhook запрещаем обращения к localhost, внутренним IP-адресам и адресам инфраструктурных сервисов.

При отправке необходимо учитывать DNS-подмену и запрещать небезопасные перенаправления.

Это важно, поскольку сервис будет выполнять HTTP-запросы на адреса, которые задаются через административную панель.

## 12.4. Лимиты и защита от злоупотреблений

Вводим ограничения на число запросов для каждого API-ключа.

Отдельно ограничиваем количество незавершённых платежей, максимальный размер `metadata`, длину строк и объём входящих webhook.

Также необходимо предусмотреть защиту административного интерфейса от перебора паролей, CSRF и несанкционированного изменения конфигурации.

Платёжный сервис не должен принимать и хранить полные данные банковских карт.

# 13. Docker и эксплуатация

## 13.1. Состав контейнеров

Для первой версии:

```text
kazna-api
kazna-worker
postgres
caddy
```

Один Docker-образ Go-приложения может использоваться для запуска API и worker.

Это упрощает сборку и обновления.

PostgreSQL должен использовать постоянный volume.

## 13.2. Конфигурация

Основные параметры:

```env
APP_ENV=production

PUBLIC_URL=https://payments.example.com

DATABASE_URL=postgres://...

MASTER_ENCRYPTION_KEY=...

ADMIN_PASSWORD_HASH=...

LOG_LEVEL=info

WORKER_CONCURRENCY=5

PAYMENT_POLL_INTERVAL=30s

# Provider integration (see VERIFICATION_HARNESS.md).
# Base URL of the YooKassa API; overridden on the stand to point at the emulator.
YOOKASSA_API_URL=https://api.yookassa.ru
# How long a repeated provider idempotency key is treated as the same request.
# Shortened on the stand (e.g. 30s) so expiry tests do not wait a day.
PROVIDER_IDEMPOTENCY_WINDOW=24h
```

Это пример предполагаемого конфигурационного интерфейса.

При реальной реализации лучше использовать Docker secrets или аналогичный механизм доставки секретов, а не хранить их в открытом `.env` на общем сервере.

## 13.3. Развёртывание

Процесс установки должен сводиться к настройке окружения и выполнению:

```bash
docker compose up -d
```

При первом запуске автоматически применяются миграции базы данных.

Административный аккаунт создаётся отдельной командой первоначальной настройки.

Должны быть предусмотрены команды проверки конфигурации и состояния системы.

## 13.4. Резервное копирование

Ежедневного `pg_dump` недостаточно для действительно надёжного платёжного сервиса, если важно сохранить все последние операции.

Для production рекомендую резервные копии PostgreSQL с архивированием WAL, чтобы обеспечить восстановление на конкретный момент времени.

Копии должны находиться на отдельном хранилище.

Процедура восстановления должна проверяться на практике.

После восстановления система обязана сверить незавершённые платежи с ЮKassa и восстановить очередь доставки событий.

Для небольшого MVP можно начать с одной базы данных, но необходимо понимать, что один VPS остаётся единой точкой отказа.

## 13.5. Мониторинг

Предусматриваем три служебных endpoint:

```http
GET /health/live
GET /health/ready
GET /metrics
```

Первый проверяет, работает ли процесс.

Второй показывает готовность принимать запросы, включая доступность необходимых зависимостей.

Третий предоставляет технические метрики.

Нужно отслеживать количество созданных платежей, ошибки обращения к ЮKassa, продолжительность операций, число незавершённых платежей, длину очереди событий и время последней успешной обработки фоновых задач.

Отдельно создаём предупреждение для платежей, которые слишком долго находятся в неопределённом состоянии.

Для MVP достаточно структурированных JSON-логов и Prometheus-совместимых метрик с простым внешним мониторингом.

# 14. Подробный план разработки по этапам

Теперь самое практическое.

Я предлагаю разделить разработку на восемь последовательных этапов, каждый из которых должен завершаться работоспособным и проверяемым результатом.

## Этап 1. Проектирование контрактов и каркаса

**Цель:** создать основу проекта, на которую будут опираться остальные модули.

Создаём Go-модуль, структуру каталогов, конфигурацию окружения, Dockerfile, Docker Compose и подключение PostgreSQL.

Настраиваем Chi, pgx, sqlc и систему миграций.

Разрабатываем OpenAPI-спецификацию основных публичных методов.

Отдельно фиксируем внутреннюю модель состояний, правила идемпотентности и обработку ошибок.

На данном этапе также создаётся минимальная архитектурная документация, содержащая принятые решения.

**Критерий готовности:** приложение собирается, запускается в Docker, подключается к базе, успешно проходит healthcheck и предоставляет документированный API-контракт.

Остальные модули могут быть заглушками.

## Этап 2. Приложения, авторизация и ключи

**Цель:** реализовать подключение независимых клиентов.

Разрабатываем модуль `applications`.

Реализуем создание приложений, выпуск API-ключей, отзыв ключей, проверку прав и изоляцию данных.

Создаём структуру для хранения подключений ЮKassa.

Добавляем шифрование секретов и функциональность проверки подключения.

На этом этапе можно использовать простые административные HTTP-методы без готового интерфейса.

**Критерий готовности:** два приложения с разными API-ключами проходят авторизацию независимо друг от друга и не могут получить доступ к данным друг друга.

Настройки ЮKassa сохраняются в зашифрованном виде.

## Этап 3. Платёжное ядро и адаптер ЮKassa

**Цель:** реализовать первый полный цикл создания платежа.

Создаём доменные модели, state machine, таблицы платежей, операции и репозитории.

Реализуем адаптер ЮKassa, создание платежа, получение статуса и нормализацию ответов.

Добавляем механизм идемпотентности и защиту от параллельного создания нескольких платежей одного заказа.

Создаём endpoint `POST /v1/payments` и получение статуса.

**Критерий готовности:** тестовое приложение создаёт платёж через наш API, получает `checkout_url`, пользователь проходит тестовую оплату, после чего сервис способен получить правильный статус через ЮKassa.

Повторный запрос с тем же ключом не создаёт второй платёж.

## Этап 4. Фоновая обработка и восстановление

**Цель:** обеспечить надёжность при сбоях.

Реализуем отдельный worker.

Добавляем очередь заданий в PostgreSQL, безопасную блокировку задач, тайм-ауты, повторы запросов и восстановление прерванных операций.

Реализуем периодическую сверку состояния платежей через ЮKassa.

Особое внимание уделяем ситуациям, когда сетевой запрос завершился без ответа, но провайдер мог выполнить операцию.

**Критерий готовности:** после перезапуска сервиса незавершённые операции продолжают обрабатываться, а платёж успешно подтверждается без входящего webhook.

Ни один неопределённый результат не приводит к автоматическому созданию новой операции с другим ключом.

## Этап 5. Webhook и система событий

**Цель:** гарантировать сохранение и повторную доставку информации о платежах.

Создаём endpoint приёма уведомлений ЮKassa.

Реализуем проверку их достоверности.

Добавляем Transactional Outbox, очередь доставки событий и механизм повторных попыток.

Реализуем подписание исходящих webhook и журнал доставки.

**Критерий готовности:** при недоступности приложения событие сохраняется, а после восстановления доступности доставляется.

Дублирующиеся события не создают повторных изменений состояния.

## Этап 6. SDK и административный интерфейс

**Цель:** сделать интеграцию действительно простой.

Создаём минимальный административный интерфейс с возможностью добавить приложение, подключить магазин ЮKassa, получить API-ключ и просмотреть платежи.

Разрабатываем Python SDK и TypeScript SDK.

Реализуем функции `pay()`, `get()`, `is_paid()` и обработку событий.

Добавляем готовые примеры подключения.

**Критерий готовности:** новый продукт подключается через административную панель, после чего разработчик создаёт платёж несколькими строками кода.

В самом продукте нет ключей ЮKassa.

## Этап 7. Тестирование надёжности

**Цель:** проверить не только успешные сценарии, но и сбои.

Создаём интеграционные тесты с настоящей PostgreSQL и эмулятором API ЮKassa.

Проверяем параллельные запросы, повторную отправку webhook, недоступность приложения, сетевые тайм-ауты, перезапуск worker и восстановление операций.

Тестируем изоляцию приложений и безопасность API.

Проводим end-to-end тесты с тестовым магазином ЮKassa.

Официальный тестовый режим позволяет проверять платежи и основную функциональность API без реального движения денег. [ЮKassa](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing?utm_source=chatgpt.com)

Тесты этого этапа живут внутри репозитория Казны и выполняются в его CI. Обязательная приёмка тех же сценариев (раздел 15) дополнительно прогоняется чёрным ящиком в [kazna-verification](https://github.com/dmitriy-zverev/kazna-verification) против собранного Docker-образа (см. [VERIFICATION_HARNESS.md](VERIFICATION_HARNESS.md)). Внутренние тесты не заменяют приёмку, но остаются обязательными.

**Критерий готовности:** все обязательные сценарии проходят автоматически во внутренних тестах, а приёмочный прогон в kazna-verification зелёный; выявленные ошибки воспроизводятся отдельными тестами.

## Этап 8. Production-подготовка

**Цель:** подготовить систему к использованию собственными продуктами.

Настраиваем HTTPS, секреты окружения, резервное копирование, мониторинг и логирование.

Создаём скрипты установки, обновления и восстановления.

Разворачиваем сервис на сервере и подключаем первое реальное приложение.

После проверки тестового окружения проводим контрольный реальный платёж и проверяем весь цикл от создания заказа до получения подтверждения приложением.

**Критерий готовности:** сервис работает независимо от приложений, восстанавливается после перезапуска, имеет проверяемые резервные копии и предоставляет достаточную диагностику для разбора неуспешных операций.

# 15. Какие тесты обязательны перед релизом

Я выделяю этот раздел отдельно, потому что платёжная инфраструктура не должна считаться готовой только после успешного прохождения happy path.

Автоматическое исполнение таблицы ниже и проверка [финансовых инвариантов](FINANCIAL_INVARIANTS.md) выполняются **независимым репозиторием** [kazna-verification](https://github.com/dmitriy-zverev/kazna-verification) против собранного Docker-образа Казны. Конфигурационные швы для стенда описаны в [VERIFICATION_HARNESS.md](VERIFICATION_HARNESS.md). Unit- и integration-тесты внутри репозитория Казны не заменяют эту приёмку.

| Сценарий | Ожидаемое поведение |
|---|---|
| Повторный `pay()` с тем же ключом | Не создаётся второй платёж |
| Два одновременных `pay()` | Создаётся только одна активная попытка |
| Сумма изменилась при том же ключе | HTTP 409 |
| ЮKassa не отвечает | Операция остаётся восстановимой |
| Ответ ЮKassa потерялся | Повтор с сохранённым ключом |
| Перезапуск API при создании | Worker восстанавливает обработку |
| Перезапуск worker | Незавершённые задания продолжаются |
| Повторный webhook ЮKassa | Нет повторного перехода состояния |
| Webhook не поступил | Статус определяется через API |
| Приложение недоступно | Событие остаётся в очереди |
| Приложение восстановилось | Событие доставляется повторно |
| Webhook подделан | Оплата не подтверждается |
| Чужой API-ключ | Доступ запрещён |
| Неверные реквизиты магазина | Понятная ошибка подключения |
| Сбой PostgreSQL | Нет подтверждения незафиксированных операций |
| Восстановление из резервной копии | Данные сверяются с провайдером |
| Старый webhook после успешной оплаты | Статус не откатывается назад |
| Истёк период идемпотентности | Неизвестная операция не создаётся заново автоматически |

Особенно важно добавить тестирование конкурентного доступа к базе.

Для этого используем реальные параллельные запросы к PostgreSQL, а не только mock-объекты.

Тесты должны воспроизводить ситуации, при которых несколько экземпляров worker одновременно пытаются обработать одно задание.

Также требуется проверить, что после сбоя между обновлением состояния платежа и доставкой события последнее всё равно будет отправлено.

# 16. Требования к производительности

Для первой версии нет необходимости стремиться к тысячам платежей в секунду.

Лучше оптимизировать систему под небольшую, но надёжную нагрузку.

В качестве начальных проектных ориентиров предлагаю следующие показатели.

| Параметр | Начальная цель |
|---|---|
| Подключённых приложений | 10–100 |
| Создание платежа | Зависит от ответа ЮKassa |
| Задержка собственного API | p95 < 100 мс без внешних вызовов |
| Обработка webhook | p95 < 300 мс при нормальной нагрузке |
| Конкурентные worker-задания | 5–20 |
| Потеря подтверждённых записей при штатном рестарте | 0 |
| Необработанные события после восстановления | Автоматическая повторная доставка |

Это внутренние цели разработки, а не измеренные характеристики будущего сервиса.

Для начала можно использовать VPS с 2 vCPU и 4 ГБ RAM.

Для Go-сервиса такая конфигурация с запасом подходит как стартовая, но реальные требования нужно определить по нагрузочным тестам и настройкам PostgreSQL.

Доступность уровня 99,99% на одном VPS обещать нельзя.

Такая цель потребует резервирования инфраструктуры, базы данных, сетевых компонентов и тестирования переключения при отказах.

# 17. Рекомендуемый порядок разработки с ИИ-агентами

Здесь я бы применил достаточно строгий подход.

Не стоит давать одному агенту задачу «разработай весь платёжный сервис». Скорее всего, он создаст работоспособную демонстрацию, но пропустит часть критических граничных сценариев.

Лучше разбивать работу на небольшие самостоятельные задачи с явными контрактами.

Например, сначала агент создаёт спецификацию API и миграции базы.

После проверки другой этап посвящается только модулю приложений и авторизации.

Затем реализуется доменная модель платежа.

После её стабилизации добавляется адаптер ЮKassa.

И только потом — асинхронное выполнение и восстановление операций.

Я бы также использовал разделение ролей.

**Planning agent** отвечает за технические решения, формулирование задач и определение контрактов.

**Coding agent** реализует отдельные модули.

**Review agent** независимо проверяет код, транзакционность, обработку ошибок и соответствие требованиям.

**Testing agent** создаёт негативные тесты и пытается воспроизвести нарушения инвариантов.

При этом критические решения — изменение состояния денег, правила повторения внешних операций и безопасность ключей — должны проходить дополнительную независимую проверку.

Для платёжных систем особенно опасна ситуация, когда один агент пишет реализацию, а затем подтверждает её корректность собственными тестами, не рассматривая альтернативные сценарии отказов.

## Документы, которые нужно создать в репозитории

Я бы предусмотрел пять основных документов.

`ARCHITECTURE.md` описывает систему, модули и их взаимодействие.

`API.md` или `openapi.yaml` фиксирует внешние контракты.

`PAYMENT_LIFECYCLE.md` описывает состояния платежей, допустимые переходы и правила идемпотентности.

`RELIABILITY.md` содержит алгоритмы восстановления, повторных запросов и обработки неопределённых состояний.

`SECURITY.md` описывает хранение ключей, авторизацию, проверку webhook и эксплуатационные ограничения.

Эти документы следует создать до написания основной бизнес-логики.

Они станут постоянным контекстом для ИИ-агентов и снизят вероятность противоречивых решений.

# 18. Критерии готовности MVP 1.0

Я бы не выпускал первую версию, пока не выполняются следующие условия.

**Интеграция.** Новый продукт можно подключить через административную панель, используя реквизиты ЮKassa. После получения API-ключа разработчик вызывает `pay()` и получает ссылку на оплату.

**Независимость.** Несколько приложений могут использовать один платёжный сервис, при этом их данные, ключи и операции изолированы.

**Надёжность.** Повторные запросы не создают случайные дополнительные платежи. При перезапуске сервиса система может восстановить незавершённую обработку.

**Подтверждение оплаты.** Успешная оплата подтверждается по данным ЮKassa. Сервис может работать без настроенного webhook, используя фоновую сверку.

**Доставка событий.** После подтверждения платежа событие сохраняется и доставляется приложению с возможностью повторных попыток.

**Безопасность.** Ключи ЮKassa не раскрываются приложениям и хранятся зашифрованными. API-ключи изолируют приложения друг от друга.

**Диагностика.** Для каждой операции можно определить её текущее состояние, историю обработки и причины ошибок.

**Развёртывание.** Сервис устанавливается через Docker Compose, поддерживает миграции, резервные копии и восстановление.

Если все эти требования выполнены, у нас действительно есть первая пригодная для эксплуатации версия, а не просто HTTP-прокси для ЮKassa.

# 19. Что сознательно откладываем до версии 1.1–2.0

После выпуска стабильного платёжного ядра я бы развивал продукт в следующем направлении.

### Версия 1.1 — удобство

Добавляем готовые шаблоны продуктов, конфигурацию цен, расширенную историю операций и более удобное управление webhook.

Тогда можно будет вызывать:

```python
payment = await payments.pay(
    product_id="pro_monthly",
    order_id="order_123"
)
```

При этом сумма и параметры чека будут определяться автоматически.

Также стоит добавить Go SDK, готовые интеграции с Django и распространёнными Node.js-фреймворками.

### Версия 1.2 — платежные операции

Полноценные возвраты, улучшенная диагностика, ежедневная финансовая сверка и инструменты ручного разрешения проблемных операций.

Важно отличать подтверждение платежа от сверки фактических взаиморасчётов с провайдером. ЮKassa отдельно предоставляет реестры успешных платежей и возвратов для финансовой сверки. [ЮKassa](https://yookassa.ru/developers/payment-acceptance/after-the-payment/reports?utm_source=chatgpt.com)

### Версия 2.0 — расширение провайдеров

Добавляем Т-Банк и другие подходящие платёжные системы.

Появляется возможность выбирать провайдера для приложения и переключать новые платежи между доступными подключениями.

Уже существующие платежи продолжают обслуживаться тем провайдером, через которого они были созданы.

### Версия 2.1 — подписки

Создаём отдельный billing-модуль.

Он будет отвечать за тарифы, подписки, периоды оплаты, продления, отмены и повторные списания.

При этом само платёжное ядро останется независимым.

# 20. Итоговая оценка реализации

Для разработчика, использующего ИИ-агентов, я бы заложил примерно следующую трудоёмкость.

| Направление | Оценка |
|---|---|
| Архитектура и контракты | 2–3 дня |
| База данных и авторизация | 3–5 дней |
| Платёжное ядро | 4–6 дней |
| Интеграция ЮKassa | 2–4 дня |
| Worker и восстановление | 4–7 дней |
| Webhook и outbox | 3–5 дней |
| SDK и административная панель | 4–7 дней |
| Тестирование и production-подготовка | 5–10 дней |

Это ориентиры активной разработки, а не календарный график или обещание готовности.

При хорошей организации и использовании ИИ-агентов функциональный MVP можно собрать быстрее. Но на проверку платёжных сценариев экономить нельзя.

Для первой версии, которой можно доверить реальные платежи нескольких продуктов, я бы закладывал примерно **5–8 недель с учётом тестирования, исправлений и проверки инфраструктуры**.

## Главное архитектурное решение

Для нашего случая оптимальная система выглядит так:

```text
                  YOUR APPLICATIONS
                          │
                          │
                        pay()
                          │
                          ▼
                ┌──────────────────┐
                │                  │
                │     KAZNA        │
                │                  │
                │   Auth + API     │
                │   Payments       │
                │   Providers      │
                │   Events         │
                │   Reconciliation │
                │                  │
                └────────┬─────────┘
                         │
                  ┌──────┴──────┐
                  │             │
                  ▼             ▼
              PostgreSQL     YooKassa
```

При этом самое важное решение, которое я бы зафиксировал в качестве неизменяемого требования:

**Приложение должно знать только наш API. Вся логика ЮKassa, включая её ошибки, статусы, webhook, повторные запросы и особенности протокола, должна находиться внутри платёжного сервиса.**

Второе требование не менее важно: **надёжность сервиса не должна зависеть от того, настроил ли пользователь webhook в ЮKassa**. Система самостоятельно отслеживает свои платежи и восстанавливает пропущенные операции.

Именно сочетание этих двух свойств сделает проект полезным для всей твоей инфраструктуры: новое приложение просто получает ключ и вызывает `pay()`, а сложная платёжная логика реализована и поддерживается в одном месте.

**Я бы начинал разработку с этапов 1–3, не переходя к интерфейсу и SDK, пока не будут стабилизированы модель платежа, идемпотентность и контракт API.** Это позволит построить действительно надёжное ядро, на которое затем можно безопасно добавлять всё остальное.
