# Финансовые инварианты Казны

Правила ниже не должны нарушаться ни при каких сбоях сети, перезапусках процессов или повторной доставке webhook. Независимый стенд [kazna-verification](https://github.com/dmitriy-zverev/kazna-verification) проверяет их через публичный HTTP API, журнал эмулятора ЮKassa, PostgreSQL и счётчик исходящих webhook.

## Идемпотентность и попытки оплаты

1. Повторный запрос создания платежа с тем же `Idempotency-Key` и тем же телом не создаёт второй платёж у провайдера и не создаёт вторую строку активной попытки для того же заказа.
2. Запрос с тем же ключом и другим телом возвращает `409 Conflict` (`IDEMPOTENCY_CONFLICT`).
3. Для одного `order_id` в приложении не может существовать более одной незавершённой (не терминальной) попытки оплаты.
4. При неизвестном результате создания у провайдера сервис не создаёт новый внешний платёж с новым ключом идемпотентности провайдера автоматически.
5. После истечения окна гарантированной идемпотентности провайдера неизвестная операция не пересоздаётся автоматически; допустим переход в `NEEDS_REVIEW` или эквивалент, но не «тихий» второй платёж.

## Подтверждение оплаты

6. Статус `succeeded` нельзя установить без подтверждения от провайдера (авторизованный `GET` платежа у ЮKassa или эквивалентная сверка).
7. Поддельный или неподписанный входящий webhook не переводит платёж в `succeeded`.
8. Повторный входящий webhook с тем же событием не меняет терминальный статус и не создаёт дублирующее исходящее событие приложению.
9. Запоздалый webhook не откатывает платёж из `succeeded` в неуспешное состояние.

## Возвраты

10. Сумма возврата не превышает доступную к возврату сумму по платежу.
11. Успешный возврат не заменяет статус исходного платежа: платёж остаётся `succeeded`, возврат — отдельная операция.
12. Повтор возврата с тем же ключом идемпотентности не создаёт вторую операцию у провайдера.

## Изоляция и секреты

13. Запрос с API-ключом приложения A не даёт доступа к платежам, заказам и событиям приложения B.
14. Секреты магазина ЮKassa не возвращаются в API-ответах, исходящих webhook приложений и логах стенда.
15. Приложение не может указать чужой `application_id` в запросе и обойти изоляцию.

## Согласованность данных

16. Количество платежей, созданных у провайдера для данной операции, согласовано с числом записей попыток/платежей в PostgreSQL (не больше одной активной попытки на заказ).
17. Исходящее событие об успешной оплате не теряется безвозвратно: при недоступности приложения оно остаётся в очереди и доставляется после восстановления.
18. Переход платежа в терминальный статус и постановка события в outbox согласованы (нет «успеха» без события, которое должно быть доставлено).

## Сверка и восстановление

19. Если входящий webhook не пришёл, worker доводит статус до терминального через опрос провайдера.
20. После перезапуска API или worker незавершённые операции продолжают обрабатываться без создания дубликатов у провайдера.

Соответствие сценариям из раздела 15 [TECHNICAL_PLAN.md](TECHNICAL_PLAN.md) проверяется автоматически в kazna-verification, а не unit-тестами внутри репозитория Казны.
